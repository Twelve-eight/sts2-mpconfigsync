# 2026-09-10 深夜联机事故分析 (Session 2)

用户报告: "游戏爆炸了" + "一进房游戏就未响应" + 多次"分歧".

## 现场证据

### 时间线 (live godot.log, 当前 session)

1. epoch 1 大厅: 4 人连接, MpConfigSync 推送 53 条配置
2. checksum 0 (玩家回合开始后) 三个 client 同时分歧 -> 断线
3. epoch 2/3/4 重试: 再次推送 53 条, checksum 1 再次分歧
4. epoch 5: 进房未响应 ~1 分钟 (读档加入流程, 262KB 状态包), 后恢复
5. 用户继续玩: 游戏活着, 6 次分歧记录 (多数被 RitsuLib 弹窗拦截显示)

### 关键排除: MpConfigSync 不是分歧原因

- **23:41:44 的分歧包 (我们 mod 部署前 23:12 但该 session 未加载它)**: 11 个字段分歧,
  checksum 0, 同样 "After player turn start". mod 集合 35 vs 25, 无 MpConfigSync.
  => 分歧在我们 mod 存在之前就以相同形态发生.
- 我们推送的 ConfigSyncMessage 对端没有此 mod => NetMessageBus 丢弃未知消息 id
  ("assuming non-gameplay"), 对端状态零改变 => 推送本身不可能造成差异.
- 主机侧日志确认 "Config sync: pushed 53 entries" 只是发出, 没有任何对端应用.

### 真实根因 (按证据强度排序)

1. **mod 集合不等 (36 vs 26), 引擎校验被强行放行**. host-only 的 10 个 mod 里
   ViolaSnakeBite 在 ModelDb 注册了 CRASH_LANDING 卡 (log: "registered in ModelDb
   but is not contained in any card pool"), 其余是纯本地表现.
   IgnoreMpModDifferences=true 跳过了引擎的 mod 集合校验, 差异全部进入对局.
2. **AutoAnthony CHAOS 局 + 两端运行时注解漂移**: 状态转储逐行多重集比对,
   唯一实际差异 = 关键字行: host 侧 CHAOS_WATCHER_CARD001=Exhaust / 002=Retain /
   003=Exhaust / 007=Exhaust, peer 侧 001=Retain / 009=Retain.
   同 ID 同名的混沌卡两端运行时关键字不同 => 两端对 AA 生成的卡模型的动态
   注解 (Retain/Exhaust 关键字在保留/消耗状态下由引擎运行时附加) 或 AA 生成
   侧效果不一致. 卡名全部相同 => 种子->名字生成是确定且一致的; 分歧在
   效果/关键字层.
3. AAW 载体警告 ("没拿到房主的生成模式载体") 两端都没出现 => AA 设置载体
   同步正常, 排除设置缺失路径.

### 未响应 (一进房卡死)

- 发生在 LOAD-RUN 加入 (ClientLoadJoinRequest -> 262144B ClientLoadJoinResponse).
- 日志无异常无崩溃, 主线程在发送/序列化大状态包期间阻塞 UI ~1 分钟后恢复.
- 丢包率当时 18-34% (NetQualityTracker), 142ms ping. 大包 + 高丢包 + 可靠通道
  重传 = 长时间无响应观感. 属网络/引擎层面, 与我们 mod 无关 (我们补丁在
  InitializeShared, 远在加入流程完成后才触发).

## 结论

- MpConfigSync 在两端都安装前无法生效 (消息被对端静默丢弃), 也无害.
- 分歧 = mod 集合不等 + AA 混沌局的固有脆弱面, 从昨天起就存在.
- 修复路径 (按优先):
  1. 队友装齐 host 的 36 个 mod (至少装会注册 ModelDb 内容的: ViolaSnakeBite).
  2. 或者 host 卸载 peer 没有的 mod (联机专用 profile).
  3. MpConfigSync 价值不变: 两端都装后, 配置类分歧源被消除 (它解决的是
     "设置不同" 这一类, 不是 "mod 集合不同" 那一类 - 后者引擎本身有校验,
     被我们的 IgnoreMpModDifferences 放行豁免了).

## 后续动作建议

- 联机时用 "mod 集合对齐" 的启动方案 (QuickLink/ModConfig 有 profile 切换?).
- IgnoreMpModDifferences 的语义重新评估: 它跳过了 mod 集合校验, 把 "该挡住的
  拦下来" 变成了 "放进局里炸". 建议联机默认关, 让引擎直接拒绝不匹配的房,
  比局内分歧断线体验好.
